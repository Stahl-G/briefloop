# 报告篇幅：建议与明确严格限制

默认采用建议篇幅：`target_words` 是建议目标，`max_words` 是建议范围的上沿。旧报告只有这两个数字时仍按建议处理，不推断用户选择了严格限制，也不改写历史要求或核查记录。中文每字计 1，连续英文或数字串计 1；标题、摘要、表格计入正文，来源标记、URL、格式和独立研究记录不计入。

超过建议范围时，写稿检查保留实际数量与差距，并将它放入 `notes` 的 `advisory`。模型应根据重复、离题或阅读负担决定是否精简；不能仅为消除提示反复改稿、删引用或采用条件。低于目标也不等于覆盖不足，不鼓励无信息量扩写。`over_limit` 保留为机械比较字段，不能单凭它判报告失败。

只有明确严格要求才使用 `length_mode="strict"`，同时提供正整数 `max_words` 和 `length_requirement`：

- 网页用户明确选择“我要求严格上限”后，记录 `kind="user_selection"` 与选项及数值说明。界面保存和回读该来源；普通预设、旧 `max_words` 和语言自动切换不会生成这类选择记录。数字被预设改变或报告语言切换后，严格来源需重新确认；即使数字相同，也不能把中文字符上限直接当成英文词数上限。
- 主 Agent 从用户要求整理严格限制时，使用 `kind="user_quote"`，`text` 为连续逐字原话，原话必须保留在 `objective`、`raw_input` 或 `writing_preferences`。程序验证原文包含关系，不用关键词猜测用户意图。Agent 不应生成 `user_selection`。从对话应用到表单的要求块不能将模型声称的界面点击作为来源。

从讨论只带入严格上限、未指定目标值时，表单将原有建议目标收至上限以内，与后台默认规则一致；显式指定的目标不会被改写，目标高于上限时仍要求修正冲突。

这是写作要求的出处记录，不是新的权限或身份认证机制：通用 API 会接纳有结构来源的要求，不能据此声称已独立证明某个人真的点击过界面，或证明引用语义必然是严格上限。用户原话的实际含义仍须由 Agent 和审阅者对照。

严格上限超出时，检查返回 `explicit_requirement`，同时列差距与来源；`length_stats` 中返回 `length_mode`、`length_requirement` 和 `strict_exceeded`。这不是事实错误标签。普通工作稿仍可提交、保存、编辑和下载；正式交付沿用既有证据与审阅门槛，不新增一个机器字数放行闸门。必要内容与严格篇幅冲突时说明冲突，而不是删掉会改变结论的条件。

软模式不改变原有读者约定的指纹，严格要求的模式与来源进入新约定身份。已经冻结的任务包和历史检查回执不被静默改写。写作、修订、评价和独立审阅共用篇幅说明；界面显示的是当前稿件所属任务的要求，而不是新建表单的值。

实现检查包括旧值与指纹兼容、严格来源验证、软/严格超长稿经过实际写稿检查与提交后保存及 Word 导出、引用与采用条件保留，以及表单选择/回读和反馈。它们证明接口行为，不证明真实模型一定减少返工。Issue #814 的真实小型验收仍须保留首稿、改稿次数和最终稿，并人工核对必要内容。
