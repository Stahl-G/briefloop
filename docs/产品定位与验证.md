# 产品定位与验证边界

BriefLoop 面向需要定期整理材料、写内部简报并核对依据的行业研究、战略和 IR 使用者。用户先提供目的、材料与约束，得到持续可编辑的稿件，再核对问题、修订并按需交付。它保留写作能力与核验链，不把一般模型输出当成可以直接发布的结论。

## 关键取舍

- 保留原件与来源快照，绑定具体稿件版本和原文位置。匹配是**指定位置内**的唯一落点，不要求某段话在整份原件只出现一次。
- 程序负责可确定的版本、哈希、引用和已绑定数值检查；Agent / Reviewer 负责语义、主体、期间、口径、因果与覆盖。两者都有失败边界。
- 低分不隐藏稿件。正式交付按已记录的独立审阅和确定性条件决定，明确重大问题不能被高分抵消；这仍然依赖主张提取、覆盖与审阅判断，不能保证“错误零放行”。
- 冲突面板用于登记、处理和复核已经发现的分歧，不承诺自动找全所有冲突。来源标签与新日期也不能自动证明哪方正确。
- Wiki 保存有依据的修订经验，候选技能经过比较后自动启用或保留原版，可回退。一次候选被拒绝只能证明该次选择路径工作，不能证明所有无效改进都能挡住。
- 当前保持单人本地工作台。Windows/Electron、团队服务和批量调度另行规划；不会为了省去安装就开放网络访问或共享凭据。

## 怎样验证价值

功能验证与效果评测分别记录。合成示例可以验证保存、改稿、导出和未审阅状态；自动测试可以验证已构造条件下的限制。它们不能证明真实报告准确率、领域覆盖率或减少人工返工。

评估真实收益时，可由使用者选少量已获准的历史任务，固定材料快照、要求、模型、推理档位与工具条件，分别保留基线和 BriefLoop 输出。人工核对数字/期间/口径错误、引用可核率、重要缺口遗漏，以及生成加人工修改的总耗时和费用。记录失败与未完成，不为获得正向结果反复采样。

这个方案尚不是实测结果。尚未验证的用户留存、付费意愿、上级退回率、与其它产品的优劣，不作为当前产品卖点。公开的 WikiSkill 研究条件也不能直接代表 BriefLoop 整篇报告的净收益。
