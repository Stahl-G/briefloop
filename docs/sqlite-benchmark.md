# ControlStore 的 SQLite 测量与只读诊断

本页仅针对 BriefLoop `Store` 使用的 **`briefloop.db`**。内置 Agent SDK 可以有自己的数据库和 journal 配置，本测量不代表整个 App 的所有 SQLite 数据库都采用同一模式。

当前 `Store` 已随 #854 加入有条件 WAL：SQLite 3.51.3+、3.50.7–3.50.x、3.44.6–3.44.x 通过现有版本门槛时，在初始化后尝试启用 WAL，并报告实际模式。其他运行库不会主动启用 WAL；文件系统不支持或锁占用使切换失败时，保留原模式。下面 2026-09-28 的 DELETE 基准是实现前的历史结果，不是当前所有工作区的默认模式。

WAL 是数据库的持久设置，换用另一 Python 解释器不会自动恢复 DELETE。未通过上述门槛的运行库在已有 WAL 工作区上初始化或写入时，会在事务内、应用写入之前报兼容错误；请使用含 WAL 修补的 Python 运行库重新打开。产品不自动降级日志模式，也不删除 `-wal` / `-shm`。已有已提交数据保留，受支持运行库仍可打开和写入。

这些门槛沿用 [SQLite 官方 WAL-reset 说明](https://sqlite.org/wal.html#walreset)的修复版本范围，不代表所有文件系统、发行环境或掉电场景已经验证。本次合成回归没有复现数据损坏，不能将兼容缺口描述成用户数据库已损坏。工作区原数据、模型任务、网络服务均不参与下面的合成基准。

## 运行便携基准

先在仓库开发环境安装项目及依赖，再选择一个**尚不存在**的结果目录：

```sh
python scripts/benchmark_store_sqlite.py run --out /path/to/new-results --processes 1 4 --cycles 25
```

Windows PowerShell 同样使用该脚本和参数，例如 `--out .\results\sqlite-new-run`。脚本使用 Python 的 `spawn` 多进程，不依赖 `ps`、`resource` 或平台特定资源监测。结果目录已存在就拒绝执行，不删旧数据重跑。`--processes` 限 1–8 个进程，`--cycles` 限每进程 1–1000 个循环；默认已经足以观察有限争用，不是容量极限测试。

实际调用当前源码的 `Store`：多进程同时初始化新合成工作区，每个进程登记种子来源并创建报告，再循环登记来源、附加到报告、写事件、按指定版本 ID 接纳、同 ID 同内容重放及查询。不是用手写 SQL 的速度代替产品接纳速度；源码及脚本哈希、实际解释器和 SQLite 版本记录在 `environment.json`。从源码运行时请保留对应提交及本地改动，不能仅凭 Git HEAD 忽略未提交变更。

输出包括：

- `load-N/process-*.json`：每次操作和写事务的原始耗时、失败、SQLite 错误码。
- `load-N/summary.json`：各操作分别的 p50、p95、最大值、锁失败和进程退出码；预期条数与实际条数；每个稿件、事件及来源字节/哈希的核对。
- `recovery/summary.json`：长读期间写入的状态、进程中途退出后的已提交/未提交标记、备份还原结果。
- `metrics.json`、`metrics.csv`：可由原始记录复算的汇总；失败返回非零退出状态，已有结果仍保留。

p50 为中位数，p95 为 nearest-rank。不同操作分别统计，失败尝试保留在耗时分布中并单列计数。事务的 `connection_and_begin_s` 包含打开连接、连接 PRAGMA 及 `BEGIN IMMEDIATE`，**不是 SQLite 内部直接提供的纯锁等待时长**。默认每进程循环数相同，所以 4 进程的总工作量是 1 进程的四倍，不能当成相同总工作量的加速比。

该入口只测新合成库，不重建所有 Worker/模型场景，也不覆盖所有历史数据库迁移。进程截止时间只约束本工具启动的合成子进程；被中止或没有结果的子进程按失败保留；所属子进程不响应 terminate 时会升级 kill，确认退出后才检查静止数据库，不终止已有产品任务。

## 诊断实际运行库

```sh
# 仅诊断这个 Python 实际链接的 SQLite；不需要导入 BriefLoop。
python scripts/benchmark_store_sqlite.py diagnose
# 同时只读检查选定 ControlStore 文件的持久日志格式：
python scripts/benchmark_store_sqlite.py diagnose --database /path/to/workspace/briefloop.db
# 另存结果必须使用新文件路径：
python scripts/benchmark_store_sqlite.py diagnose --database /path/to/workspace/briefloop.db --out sqlite-diagnostic-new.json
```

请使用**真正运行目标后端的 Python**。终端默认 Python、桌面 App 自带 Python、系统 `sqlite` 命令可能链接不同的 SQLite；一个探针不替另一个环境背书。

诊断入口只用标准库，不连接用户数据库，只读取 SQLite 文件头的 100 字节；不调用 `Store` 初始化、迁移，不设置 journal、不读取报告正文或凭据。缺少文件或头部无效就报告失败。实际 Python/平台、`sqlite_version()` 和 `sqlite_source_id()` 来自该解释器的内存连接。

所选文件以 `persistent_journal_family` 报告头部的 `wal` / `rollback` 格式；`journal_mode` 为 null、`journal_mode_query` 为 `not_executed`。这是有意的边界：即使 SQLite 用 `mode=ro`，打开 WAL 库仍可能在用户目录创建 `-wal` / `-shm`。文件头不能区分 rollback 家族中的 DELETE/PERSIST/TRUNCATE，也不是活动数据快照。脚本不会用 `immutable=1` 忽略活跃 WAL 后冒充正常诊断。合成基准拥有自己的新目录，才在那里执行真实 `PRAGMA journal_mode` 查询。

`wal_patch_assessment` 明确为 `not_assessed`。版本/源码身份让维护者能够核对发行运行库及官方修补说明，脚本不把一个版本号自动认定为所有平台的安全证明，更不据此切换 WAL。发行环境、文件系统适用性和 SQLite 官方说明须单独核对。

## 恢复与备份边界

异常退出检查让子进程先提交一个标记，再在另一事务尚未提交时退出；重开后要求已提交标记保留、未提交标记不存在，且完整性与外键检查通过。这不模拟断电、硬盘损坏或全部系统故障。

备份检查只操作本工具创建的合成工作区，先等待全部所属写入线程和子进程退出，再复制来源文件，通过 **SQLite Backup API** 生成目标数据库。还原后用实际 Store 读取，并核对来源文件全集、所有数据库表的逻辑内容及 schema 哈希、稿件内容、标记、条数、完整性及外键；不是只比较数据库里保存的 hash 列。

它不是任意工作区的热备份命令；没有承诺持续写入时数据库与多份来源文件的快照一致性，也不会只复制一个可能仍在写入的 `.db` 主文件。此脚本没有清理 `-wal` / `-shm` 文件的行为。

## 既有本地有限结果（2026-09-28）

以下来自此前冻结 `7c4520b7872248908a83d224c88dd9bf124f16e4` 的私有合成基准。此次将其 SQLite 部分提炼成上述便携入口，保留原脚本、失败和原始测量；没有重新跑完整旧基准，也没有把新入口的短验证混入这些数据。

原测量环境为 macOS arm64，Python 3.14.6 / SQLite 3.50.4，所测 ControlStore journal 为 `delete`。每进程 25 次循环，1 进程共 25 次、4 进程共 100 次；每组仅一次有限样本。

| 操作 | 1 进程 p50 / p95（ms） | 4 进程 p50 / p95（ms） |
| --- | ---: | ---: |
| 来源登记 | 1.06 / 1.26 | 2.42 / 42.07 |
| 事件写入 | 0.90 / 1.13 | 0.87 / 2.23 |
| 稿件接纳 | 3.12 / 9.86 | 4.66 / 56.68 |
| 同版本重放 | 2.17 / 2.44 | 6.00 / 20.81 |
| 状态查询 | 0.23 / 0.28 | 0.28 / 5.21 |
| 连接与事务进入 | 0.075 / 0.151 | 0.110 / 10.20 |

两组没有锁失败；各次重放没有增加稿件数，125 个循环的稿件、来源和事件逐项一致，完整性和外键检查通过。最初一次夹具因“禁止联网且无来源”的需求被产品拒绝，保留并排除于数据库失败率；修正合成输入后只补跑负载项。不能把夹具失败写成数据库事故。

此前还核对了四进程新库/合成旧 schema 初始化、带来源和稿件的合成迁移、只读审阅包，以及长读释放、进程退出和静止备份恢复；这些原记录未被便携入口重复覆盖。本地已安装 Mac 0.25.0 的另一个实际解释器探针为 Python 3.12.13 / SQLite 3.53.1，与源码环境分开记录，不能替代 Windows 原生发行验证。

当前便携入口另以每进程 5 次、1/4 进程作一次小验证：25 次新稿及25次重放，来源/事件/内容、异常退出恢复及静止备份还原均通过，无锁错误。这只说明新入口可运行，不用于证明稳定性能改善。

上述历史基准没有覆盖 Windows 发行运行库、网络文件系统、WAL 对照及持续写入下的多文件热备份。#854 后续有条件 WAL 和长读期间写入/备份行为已有实现与回归（`tests/test_store_wal.py`），不将它们混入上述历史测量；网络文件系统与掉电仍未验证。没有真实模型调用，也没有模型吞吐或用户报告质量结论，不建议手工绕过运行库门槛启用 WAL。
